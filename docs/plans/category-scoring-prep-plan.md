# Category Scoring Preparation Plan

**Status:** Implemented and verified.

## Top-Level Overview

The active quiz application works correctly but has two structural problems that
must be resolved before category-level scoring can be added without creating
technical debt:

1. The only test in the project is a stale Create React App boilerplate test that
   will fail immediately because the text it looks for does not exist in the
   current app. No useful test coverage exists.

2. The results view — score summary, pass/fail message, answer-review list, and
   explanations — is inlined inside `Quiz.jsx` behind a `showResults` flag. That
   component already owns answer collection, navigation, validation, and
   submission. Adding per-category score cards to the same inline block would
   push it well past a maintainable size.

The goal of this plan is to perform the **minimum structural preparation** needed
before the category scoring feature is implemented:

- Replace the broken test with a valid smoke test.
- Extract the results section into a focused, standalone component.
- Leave all quiz logic, state, and category strings exactly where they are.
- Preserve the existing UI and user experience without alteration.

No scoring logic is added. No categories are normalised. No IBM Granite or
watsonx.ai integration is started. No authentication, database, or new
state-management library is introduced.

### Sub-Task 2 — Extract the inline results section into `QuizResults`

**Status:** [x] done

#### Intent

The results view is currently inlined inside `Quiz.jsx` as the `true` branch of
`{showResults ? ... : ...}`. Extracting it into a dedicated component
`src/components/QuizResults.jsx` achieves three things:

1. `Quiz.jsx` becomes a single-responsibility component: it owns state,
   navigation, and submission only.
2. The results view becomes independently readable and testable.
3. When category score cards are added in the next task, they are added to
   `QuizResults` in isolation — `Quiz.jsx` does not need to change.

No logic is moved. The extracted component is a pure presentational component
that receives everything it needs via props and emits one callback.

#### Expected Outcomes

- A new file `src/components/QuizResults.jsx` exists and renders identically to
  the current inline results block.
- `src/pages/Quiz.jsx` is shorter by exactly the extracted JSX block; all state
  and logic remain in place.
- The application behaves identically before and after extraction — same UI,
  same pass/fail behaviour, same review list.
- The smoke test added in Sub-Task 1 still passes after this change.

#### Todo List

1. Identify the exact JSX block to extract from `Quiz.jsx`: the outer `<section>`
   that begins at line 125 (the `showResults ? (` true branch) through the
   closing `</section>` at line 260.
2. Determine the minimum props `QuizResults` needs (see Proposed Props below).
3. Create `src/components/QuizResults.jsx`:
   - Copy the extracted `<section>` JSX verbatim.
   - Replace the five values that were referenced from `Quiz.jsx` scope
     (`score`, `questions.length`, `resultPercentage`, `quiz.passingPercentage`,
     `questions`, `answers`, `tryAgain`) with the corresponding prop names.
   - No styling changes. No logic changes.
4. Update `src/pages/Quiz.jsx`:
   - Add an import for `QuizResults` at the top.
   - Replace the extracted JSX block with `<QuizResults {...props} />`.
   - Remove any variables that are now only needed inside `QuizResults`
     (specifically `resultPercentage` — see note under Risks).
5. Verify the app renders and behaves correctly by running the development
   server and navigating through a quiz attempt.
6. Confirm the Sub-Task 1 smoke test still passes.

#### Proposed Component Interface

```
// src/components/QuizResults.jsx

Props:
  questions         — array   — the full questions array (needed for review list)
  answers           — object  — map of questionId → selectedOptionId
  score             — number  — total correct answers (integer)
  totalQuestions    — number  — questions.length, passed explicitly so the
                                component does not need to import questions.js
  resultPercentage  — number  — Math.round((score / totalQuestions) * 100),
                                computed in Quiz.jsx and passed down; keeps the
                                component stateless and the derivation in one place
  passingPercentage — number  — quiz.passingPercentage (70), passed from Quiz.jsx
                                so QuizResults does not need to import quiz metadata
  onTryAgain        — func    — the tryAgain callback defined in Quiz.jsx
```

**Decision: pass `resultPercentage` from Quiz.jsx rather than derive it inside
QuizResults.** The value is already computed in `Quiz.jsx` (line 23) and will be
needed by the category scoring feature in the next task. Keeping the derivation
in `Quiz.jsx` means there is one place to extend it.

**Decision: pass `totalQuestions` as a separate prop rather than using
`questions.length` inside the component.** This makes the prop surface explicit
and avoids the component depending on the array length implicitly.

**Decision: do NOT pass the `quiz` object.** Only `passingPercentage` is used
from it. Passing the full object creates an implicit dependency on the data
model inside a presentational component.

#### Relevant Context

- Source of the JSX block to extract:
  `src/pages/Quiz.jsx`, lines 124–260 (the `showResults` true branch, the
  outer `<section>` and everything inside it).
- `quiz.passingPercentage` is referenced at line 146 and line 151 inside the
  extracted block — this becomes the `passingPercentage` prop.
- `tryAgain` function is defined at `Quiz.jsx:92` — this becomes `onTryAgain`.
- `resultPercentage` is computed at `Quiz.jsx:23` from `score` and
  `questions.length` — it stays in `Quiz.jsx` and is passed as a prop.
- After extraction, `Quiz.jsx` no longer needs to import `quiz` for the results
  section — but it still uses `quiz.title` in the question view (line 265), so
  the import must be kept.

### Sub-Task 3 — Add a focused unit test for `QuizResults`

**Status:** [x] done

#### Intent

The smoke test from Sub-Task 1 confirms the app mounts. A dedicated test for
`QuizResults` verifies that the extraction did not silently break the results
view and provides a stable regression baseline before the category scoring
feature adds new props to the component.

The test file is kept small and focused: it does not test quiz navigation or
submission — only the results rendering logic. Fixtures are inline minimal
objects — they do not import from `src/data/questions.js` so the tests remain
isolated from content changes.

#### Expected Outcomes

- A new file `src/components/QuizResults.test.jsx` exists.
- Six test cases pass (see Todo List).
- The existing smoke test in `src/App.test.js` continues to pass.
- Total passing tests under `npm test -- --watchAll=false`: 7 (1 smoke + 6 unit).

#### Fixtures

Two inline question objects must be defined at the top of the test file. They
contain only the fields that `QuizResults` reads:

```
questionA — a question the user answers correctly:
  id: "q-a"
  prompt: "What is 2 + 2?"
  options: [{ id: "four", text: "Four" }, { id: "five", text: "Five" }]
  correctOptionId: "four"
  explanation: "2 plus 2 equals 4."

questionB — a question the user answers incorrectly:
  id: "q-b"
  prompt: "What colour is the sky?"
  options: [{ id: "blue", text: "Blue" }, { id: "red", text: "Red" }]
  correctOptionId: "blue"
  explanation: "The sky appears blue due to Rayleigh scattering."
```

`answers` map for the "one correct, one wrong" scenario:
  `{ "q-a": "four", "q-b": "red" }`

`answers` map for the "all correct" scenario:
  `{ "q-a": "four", "q-b": "blue" }`

Standard props shared across most tests:
  `questions`: `[questionA, questionB]`
  `totalQuestions`: `2`
  `passingPercentage`: `70`

## Risks and Rollback

### Risk 1 — Missed prop causes a runtime error in QuizResults

If a variable used inside the extracted JSX block is not included in the props
interface, React will throw a reference error at runtime. The risk is low because
the extracted block is a read-only copy of code that already works, but a careful
line-by-line check of every identifier in the block against the proposed props
list must be done before Sub-Task 2 is considered complete.

**Mitigation:** Run `npm start`, complete a full quiz attempt, and inspect the
results view visually before running tests.

### Risk 2 — `resultPercentage` removed from Quiz.jsx too early

`resultPercentage` is computed at `Quiz.jsx:23` and currently used only in the
inline results block. After extraction it is passed as a prop, so it must remain
in `Quiz.jsx`. If it is accidentally deleted as "unused", the prop will be
`undefined` and the percentage display will break silently (renders as `NaN%`).

**Mitigation:** The computation stays in `Quiz.jsx` explicitly; do not remove it.

### Risk 3 — Smoke test environment issue with BrowserRouter

`App.js` wraps routes in `BrowserRouter`. Testing-Library renders into jsdom,
which does not provide a real browser history. In most CRA setups this works
without a `MemoryRouter` wrapper because `BrowserRouter` falls back gracefully.
If the test throws a router error, wrap `<App />` with `<MemoryRouter>` in the
test.

### Rollback

All changes in this plan are additive or surgical replacements:

- Sub-Task 1: `git checkout src/App.test.js` restores the original (broken) test.
- Sub-Task 2: `git checkout src/pages/Quiz.jsx` + `git rm src/components/QuizResults.jsx` restores the original inline block.
- Sub-Task 3: `git rm src/components/QuizResults.test.jsx` removes the new tests.

None of the changes affect the running application's behaviour, routing,
dependencies, or data model.
